# Branding Guide

> How the ShopnoOS brand system works, and how to rebrand the distribution in under an hour.

---

## Design Goal

All branding is isolated in `brand/`. Nothing outside that directory should contain a hardcoded distribution name, color, URL, or logo path. Every build script, hook, and config file reads from `brand/identity/*.env` at build time.

The practical result: to fully rebrand this distribution, you change files in one directory and swap assets in another. No hunting through configs.

## Identity Files

### `brand/identity/name.env`

The most important file. All required variables must be present or the build will fail.

```bash
DISTRO_NAME="ShopnoOS"
DISTRO_CODENAME="Boipoka"
DISTRO_VERSION="1.0"
DISTRO_ID="shopno"
DISTRO_ID_LIKE="debian"
DISTRO_WEBSITE="https://shopno.jadupc.com"
DISTRO_BUGTRACKER="https://github.com/JaduPC/shopno-os/issues"
```

| Variable | Purpose | Constraints |
|----------|---------|-------------|
| `DISTRO_NAME` | Human-readable name shown in UI and docs | Any string |
| `DISTRO_CODENAME` | Release codename | Any string |
| `DISTRO_VERSION` | Version number | Digits and dots only: `1.0`, `1.0.1`, `2024.01` |
| `DISTRO_ID` | Machine identifier used in filenames and ISO names | Lowercase, alphanumeric, hyphens allowed — no spaces, no uppercase |
| `DISTRO_ID_LIKE` | Parent distribution (for tooling compatibility) | Keep as `debian` unless you know what you're changing |
| `DISTRO_WEBSITE` | Home URL | Full URL with scheme |
| `DISTRO_BUGTRACKER` | Bug report URL written into `/etc/os-release` | Full URL with scheme |

`DISTRO_ID` directly affects ISO filenames. Changing it changes every ISO name produced by every profile. If you are renaming mid-project, update `docs/naming-law.md` and any CI artifact references at the same time.

---

### `brand/identity/colors.env`

Used by theme hooks and any tooling that generates branded assets programmatically.

```bash
BRAND_COLOR_PRIMARY="1F4E79"
BRAND_COLOR_ACCENT="C55A11"
BRAND_COLOR_LIGHT="D6E4F0"
BRAND_COLOR_DARK="0D1B2A"
BRAND_COLOR_TEXT_ON_PRIMARY="FFFFFF"
```

All values are hex without the `#` prefix. The build system exports these as environment variables so hooks and scripts can reference them without hardcoding.

---

### `brand/identity/urls.env`

Variables in this file use the `URL_` prefix (not `DISTRO_`). They are grouped by purpose:

```bash
# Website
URL_WEBSITE="https://shopno.jadupc.com"
URL_DOCS="https://shopno.jadupc.com"
URL_SUPPORT="https://shopno.jadupc.com/support"
URL_DOWNLOADS="https://shopno.jadupc.com"

# Community
URL_FORUM=""
URL_MATRIX=""
URL_TELEGRAM=""

# Development
URL_SOURCE="https://github.com/JaduPC/shopno-os"
URL_BUGTRACKER="https://github.com/JaduPC/shopno-os/issues"
URL_CI=""

# Mirrors
URL_MIRROR_MAIN=""
URL_MIRROR_FALLBACK=""

# Security
URL_SECURITY_ADVISORIES=""
URL_GPG_KEY=""
```

Build scripts consume these directly (e.g. `prepare-lb-config.sh` reads `URL_SUPPORT`). Changing a value here propagates to every hook and script that sources `urls.env` at build time.

## How Variables Reach the Build

`scripts/lib/brand.sh` is sourced automatically at the start of every build script. It:

1. Loads all three `brand/identity/*.env` files
2. Validates required variables and format rules
3. Exports all `DISTRO_*`, `BRAND_*`, and `URL_*` vars into the environment

Every child process — including live-build hooks — inherits the exported variables. Hooks never read `brand/identity/` directly; they use the pre-exported environment.

```bash
# Any hook can reference brand vars directly:
echo "Welcome to ${DISTRO_NAME} ${DISTRO_VERSION}" > /etc/issue
```

`/etc/os-release` is generated by a hook that calls `generate_os_release()` from `brand.sh`. It is never written manually. Do not add `os-release` to `includes.chroot/`.

## Asset Reference

### Logo

| File | Use |
|------|-----|
| `logo.svg` | Default — light backgrounds, documentation, welcome app |
| `logo-dark.svg` | Dark backgrounds, dark-themed DEs |
| `logo-mono.svg` | Single-color contexts: GRUB splash, Plymouth fallback |

All three variants are required. If your logo works on all backgrounds, you may use the same SVG for all three, but the files must exist.

Scripts reference logos through helper functions in `brand.sh` — never by constructing paths manually:

```bash
source scripts/lib/brand.sh

logo_path="$(brand_logo_svg)"
```

---

### Wallpapers

| Path | Used by |
|------|---------|
| `brand/assets/wallpapers/base/shopno-os-default.png` | All flavors as the default wallpaper |
| `brand/assets/wallpapers/base/shopno-os-dark.png` | Dark mode variant |
| `brand/assets/wallpapers/editions/<edition>/` | Edition-specific wallpaper (optional) |

Flavors reference the default wallpaper via `brand_wallpaper_base()` from `brand.sh` and set it through their gschema override or skel configuration. They do not hardcode the path string.

**Required dimensions:** 1920×1080 minimum. Provide 3840×2160 (4K) if possible — it scales down cleanly, but low-resolution wallpapers look poor on HiDPI displays.

**Format:** PNG. Do not use JPEG — compression artifacts appear at boot.

---

### GRUB Theme

```
brand/assets/grub/
├── theme/          # full GRUB theme directory (fonts, icons, layout)
└── background.png  # standalone background used if no full theme
```

The `background.png` is used by the build hook even when a full theme is not configured. It must be:

- Format: PNG
- Dimensions: 1920×1080
- Color depth: 24-bit RGB (not RGBA — GRUB does not support alpha)

The GRUB theme directory follows standard GRUB2 theme conventions. Reference it in your `lb_config.sh` via `brand_grub_background()`.

---

### Plymouth Theme

```
brand/assets/plymouth/
├── theme/      # Plymouth theme files (.plymouth, images, scripts)
└── logo.png    # logo used by script-based themes
```

The `logo.png` used by Plymouth should be:

- Format: PNG with transparency (RGBA)
- Dimensions: 256×256 or 512×512
- Dark background-compatible (Plymouth shows a dark boot screen by default)

---

### `skel-branding/`

Files in `brand/skel-branding/` are overlaid onto `/etc/skel` for **all editions** during the build. Use this for global defaults that apply regardless of DE — for example, default file manager bookmarks or a shared GTK bookmark list.

DE-specific skel files (dconf databases, plasma config) belong in `flavors/<n>/skel/`, not here.

---

## How the Build Injects Branding

The branding injection sequence during a build is:

1. `brand.sh` loads and exports all `DISTRO_*` vars
2. `prepare-lb-config.sh` copies `brand/skel-branding/` into the chroot skel overlay
3. Asset hooks copy logos, wallpapers, GRUB background, and Plymouth theme into the chroot
4. The `0090-stamp-build-info.hook.chroot` hook calls `generate_os_release()` to write `/etc/os-release`
5. Flavor hooks reference wallpaper paths via `brand_wallpaper_base()` when setting DE defaults

No step writes a brand value from memory. Every injection reads from `brand/` at build time.

## Rebrand Checklist

To fully rebrand this distribution:

### Identity (required)

- [ ] Edit `brand/identity/name.env` — update all seven variables
- [ ] Edit `brand/identity/urls.env` — update all URLs
- [ ] Edit `brand/identity/colors.env` — update color palette if desired

### Assets (required)

- [ ] Replace `brand/assets/logo/logo.svg`
- [ ] Replace `brand/assets/logo/logo-dark.svg`
- [ ] Replace `brand/assets/logo/logo-mono.svg`
- [ ] Replace `brand/assets/wallpapers/base/shopno-os-default.png`
- [ ] Replace `brand/assets/grub/background.png`
- [ ] Replace `brand/assets/plymouth/logo.png`

### Assets (optional but recommended)

- [ ] Replace `brand/assets/wallpapers/base/shopno-os-dark.png`
- [ ] Replace `brand/assets/grub/theme/` with a custom GRUB theme
- [ ] Replace `brand/assets/plymouth/theme/` with a custom Plymouth theme
- [ ] Replace `brand/assets/icons/shopno-os-icon-theme/` with a custom icon set

### Validation

- [ ] Run `./scripts/dev/check-no-hardcoded-names.sh` — confirms no old name leaked into configs
- [ ] Run `./scripts/dev/check-brand-vars-used.sh` — confirms all vars are consumed
- [ ] Run `./scripts/build/build.sh <any-profile> --dry-run` — confirms identity loads cleanly
- [ ] Do a full build and verify `/etc/os-release` in the live system

## Rules: What Must Never Happen

| Violation | Why It Breaks Things |
|---|---|
| Hardcoding `"ShopnoOS"` anywhere outside `brand/` | Rebrand requires grep-and-replace across the whole repo |
| Writing `/etc/os-release` manually in `includes.chroot/` | Gets overwritten by the hook; creates a confusing race |
| Constructing logo/wallpaper paths as strings in scripts | Path changes require editing every script that references them |
| Putting brand vars in `profile.env` | Profile vars are build-matrix variables; brand vars are identity — different concerns |
| Using `BRAND_*` vars before sourcing `brand.sh` | They won't exist; scripts will silently use empty strings |

## Lint Checks

Three lint scripts in `scripts/dev/` enforce branding hygiene:

```bash
# Finds any file outside brand/ containing hardcoded distribution names:
./scripts/dev/check-no-hardcoded-names.sh

# Confirms every DISTRO_* var declared in name.env is actually used somewhere:
./scripts/dev/check-brand-vars-used.sh

# Validates that brand/identity/*.env files parse correctly:
./scripts/dev/lint-packages.sh   # runs brand validation as a side effect
```

Run these before every release. They are also run automatically by the `lint-packages.yml` CI workflow on every push.
